Next-Visit Theo Model Evaluation

A rebuild of an evaluation dashboard I made during a summer analytics internship at a Las Vegas integrated resort. It shows how a model that predicts each guest's theoretical gaming win (“theo”) for their next trip performs, broken down by loyalty tier, game type, booking lead time and predicted-worth band.

About this demo. The real data is confidential, so every number here is synthetic: 8,000 made-up trips generated by scripts/generate_synthetic_data.py, with no guest data and no real results. The SQL logic, metric definitions and dashboard layout follow the queries and dashboard I wrote during the internship; table and column names are generalized. Tier names are the public loyalty-program tiers (Chairman, Black, Platinum, Red). I used AI tools (Claude) to help build this public version: generating the synthetic data, writing the HTML dashboard and editing the write-up.

The bug that wasn't a bug: averaging ratios

My first evaluation query computed the error for each trip as (actual − predicted) / actual and then averaged it by tier. The results were alarming: the top tier looked like it was off by thousands of percent, while its aggregate predictions were actually close to reality.

The cause was not the model. A small number of trips where a high-value guest barely played (actual theo of a few dollars against a prediction in the tens of thousands) produce individual errors of −1,000× or worse, and a simple average lets those few rows swamp everything else.

The fix was to normalize at the group level: normalized MAE = mean(|error|) ÷ mean(actual) and bias = (mean actual − mean predicted) ÷ mean actual. Both are weighted by dollars, which matches how the business uses the prediction (budgeting comps and marketing offers), and neither one explodes on tiny denominators.

Context

The resort's data science team had a model that predicts how much each loyalty member will be worth on their next trip (their theoretical gaming win, or “theo”), built from a range of guest data. That prediction feeds how comps and offers are sized. The team was building a successor model and needed two things: a clear way to show executives how accurate the current model really was, and a way to see where it fell short so the next version could improve on it.

What I built

  • Evaluation queries in Databricks SQL against the model's scored output table (one row per guest with prediction, actual theo and error), grouped by loyalty tier, game type, predicted-worth band, booking lead time and time.
  • A metric definition the team could trust: normalized MAE and aggregate bias at the group level, after finding that averaging per-trip percentage errors produced misleading, outlier-driven numbers (see the previous tab).
  • Booking-lead-time bins (≤15 days, then 15-day windows to 180+) with an explicit sort key, so the business could see whether predictions made further in advance were less reliable.
  • A Databricks dashboard with a “Categorical Performance” page (tier, game type, worth band) and a “Performance Over Time” page, designed so a non-technical executive could read it in a minute.

Impact

  • Gave executives a clear answer on accuracy. Individual predictions can miss, so a single guest's comp may be off, but across a tier or the whole guest base the errors average out and the model is accurate. That is the level at which the business spends money, so the model was shown to be valuable.
  • Fed the next model. The breakdowns showed the data science team exactly which segments the current model handled worst, which they used to iterate on the new model.

What the evaluation surfaced (shown here on synthetic data)

  • Accurate in aggregate, noisy per trip. Binned by predicted worth, average predicted and average actual theo line up closely, so the model is usable for budgeting a segment. But the typical single-trip miss is large, so it should not be read as a precise per-guest number.
  • Segment bias that an overall number hides. A small overall bias can sit on top of a clearly over-predicted entry tier and very-short-lead bookings.
  • Table games are harder to predict than slots, which is consistent with higher trip-to-trip volatility in table play.

What I'd do differently

  • Fix the metric definitions first. I iterated on the SQL before agreeing on what “error” meant; writing down the error and bias definitions up front would have saved several rounds of confusing results.
  • Always show counts and uncertainty. Some tier × lead-time cells had only a handful of trips. I'd add sample sizes and bootstrap intervals to every bar.
  • Treat near-zero trips as their own question. “Will this guest actually play?” deserves its own metric (hit rate), separate from “how much will they play?”.
  • Make it parameterized and reusable. One parameterized dataset instead of many near-copies of the same query, so a retrained model can be evaluated with one click.

Evaluation SQL (sanitized)

These follow the queries I wrote in Databricks for the original dashboard. Table and column names are generalized, and the booking-window query is a cleaned-up version of my original (one CTE instead of a repeated CASE statement).

-- Performance by segment (tier shown; swap the GROUP BY column for game_type, worth band, etc.)
SELECT
  tier,
  COUNT(*)                                                    AS trips,
  AVG(predicted_theo)                                         AS avg_predicted,
  AVG(actual_theo)                                            AS avg_actual,
  AVG(ABS(actual_theo - predicted_theo)) / AVG(actual_theo) * 100
                                                              AS normalized_mae_pct,
  (AVG(actual_theo) - AVG(predicted_theo)) / AVG(actual_theo) * 100
                                                              AS bias_pct,
  -- original definition, kept for comparison: explodes when actual_theo is near zero
  AVG((actual_theo - predicted_theo) / NULLIF(actual_theo, 0)) * 100
                                                              AS avg_individual_pct_error
FROM model_eval.next_trip_predictions
GROUP BY tier
ORDER BY avg_predicted DESC;

-- Booking lead-time bins: compute the bin once in a CTE, then group by it
WITH binned AS (
  SELECT *,
    DATEDIFF(day, snapshot_date, checkin_date)            AS lead_days,
    LEAST(FLOOR((DATEDIFF(day, snapshot_date, checkin_date) - 1) / 15), 12)
                                                          AS lead_bin   -- 0 = ≤15 days … 12 = 180+
  FROM model_eval.next_trip_predictions
)
SELECT
  lead_bin,
  CASE WHEN lead_bin = 12 THEN '180+ days'
       ELSE CONCAT(lead_bin * 15, '–', (lead_bin + 1) * 15, ' days') END AS booking_period,
  COUNT(*)                                                         AS trips,
  AVG(ABS(actual_theo - predicted_theo)) / AVG(actual_theo) * 100  AS normalized_mae_pct,
  (AVG(actual_theo) - AVG(predicted_theo)) / AVG(actual_theo) * 100 AS bias_pct
FROM binned
GROUP BY lead_bin
ORDER BY lead_bin;

Lesson baked into the second query: an earlier version repeated a 13-branch CASE in both the SELECT and a separate sort column and grouped by only one of them, which raised a missing-aggregation error. Computing the bin once in a CTE removes the duplication and the error.
